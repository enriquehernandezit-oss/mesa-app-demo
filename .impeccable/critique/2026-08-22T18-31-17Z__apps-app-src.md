## The one fix that didn't fully land: seed/data-layer Spanish is still English

The sweep covered every UI-chrome file (~33 files) but never touched the **data layer** that feeds those same components. This is not a stray string here or there — both assessments hit it on nearly every screen that lists a restaurant:

- **Cuisine labels are raw English everywhere** — `packages/db/src/seed-data.ts` / `seed-extra.ts`: `Italian, Dominican, Basque, Japanese, Contemporary, Mediterranean, Spanish, European, Peruvian, Tapas, Wine Bar, Brasserie, Café, Fusion, Sandwiches, Grill, Steakhouse, Pizza, Brunch, Mexican`. Renders on `/discover`, `/explore`, `/rank` find-step, `/r/:id`, `/rankings`, `/tonight`, `/map`.
- **Two vocabularies for the same concept** — `RANK_TAGS` in `RankAPlace.tsx:53` was correctly localized (`Cena romántica, Ocasión especial, Cena en grupo, Al aire libre, Solo`), but the seed's `TAGS` const (`seed-extra.ts:489-497`) is explicitly English by design comment ("Title-case, English — a controlled vocabulary"): `Date Night, Special Occasion, Group Dinner, Outdoor, Fine Dining, Casual, Late Night`. A restaurant profile shows "Date Night · Group Dinner" while the rank flow's own tag picker for the identical taxonomy shows Spanish — visible on the same product, different screens.
- **Same screen, two languages for the same fact** — `RestaurantProfile.tsx:172` hardcodes `` `${count} rankings` ``, while the same file's line 249 correctly renders `` `${count} rankeados` ``. One screen, one number, two languages.
- **Smaller misses**: `DiscoverTab.tsx:274` renders raw `dishGrain` ("film · daylight"/"film · none"); `DishCompose.tsx:15-16` grain picker chips are "Candlelit"/"Daylight" next to a Spanish "Ninguno"; `lib/time.ts:6` returns bare `"now"` for <60s-old timestamps; `lib/shareCard.ts:76` bakes the English tagline "where your friends actually eat" into the exported/shared PNG (this one leaves the app — visible to non-users); `CheersButton.tsx:48` has an English `aria-label="Cheers"` (Spanish `"Quitar cheers"` when active) — same control, two languages, screen-reader-only so a sighted QA pass would never catch it. Both A (as a Sam-persona accessibility flag) and B (via direct source read) hit this independently.

Everything else — signed-out/auth, login, onboarding, `/settings`, `/activity`, empty/error states, and date formatting (`/tonight` correctly shows "Sáb 22 ago") — reads as clean, consistently-registered Spanish.

## Anti-Patterns Verdict

Unchanged from the baseline and reaffirmed by both assessments: **not AI-generated.** Oxblood/brass two-theme system, Cormorant display numerals, film-grain photography, mono spec-sheet metadata, the reassurance microcopy pattern in the compare flow — these are specific, authored choices. No gradient text, no generic hero-metric blocks, no template card grid. The restraint (real photography, real neighborhood names, sparing use of the brass accent) is itself evidence of a considered point of view, not an AI pass.

## Overall Impression

The one thing the prior critique said was structurally missing — the social payoff at the moment of ranking — is now built, and it's built well. Both assessments independently confirmed the friends'-rankings card renders correctly, the commit-at-reveal architecture actually protects against interruption (not just in theory — B watched the network request fire before the note step), and the visual regression from the badge fix is gone. That's the headline result: **the core loop's thesis now actually fires.**

What's holding the score back is no longer the core mechanic — it's that the language-consistency work stopped at the UI-chrome boundary and never crossed into the data that UI renders. This produces a specific, recognizable failure mode: a Spanish-first user reads a fully-Spanish screen and then hits an English word sitting inside a Spanish sentence ("$$ · Dominican", "Date Night · Group Dinner"). That reads as more broken than an app that was never translated at all, because it looks like an oversight rather than a design decision. Two smaller but real cracks also surfaced under closer testing: an unreliable pairwise progress count, and a mislabeled "nuevo en tu lista" tag that persists on a re-rank of an already-ranked place (factually wrong information shown to the user, not just a copy nit).

## What's Working

1. **The reveal screen's friends card is the loop's centerpiece and it earns that role.** Concrete numbers, real names and avatars, capped at 3 with a count/average line, and a genuine empty-state ("vas primero") rather than a dead space — this is the exact fix the prior critique called for, implemented correctly.
2. **Commit-at-reveal is a real architectural improvement**, not just a bug fix — B confirmed via network log that the ranking is durable the instant the score shows, which makes the whole flow interruption-safe for a distracted mobile user (Casey), independent of whether they ever reach the note step.
3. **The reassurance copy in the compare flow** ("Tu respuesta mueve a X, no la puntuación del spot," repeated at every comparison) is a small, considered trust-building detail specific to a ranking-not-rating product.
4. **Visual restraint holds up under two independent close reads** — no AI-slop tells, no visual regressions introduced by any of the five fixes.

## Priority Issues

### [P1] Restaurant `cuisine` values are untranslated across the entire app
Renders on `/discover`, `/rank`, `/explore`, `/r/:id`, `/rankings`, `/tonight`, `/map` — every place a restaurant card appears. Data-layer issue (`packages/db/src/seed-data.ts`, `seed-extra.ts`), not a chrome miss, so it wasn't caught by a screen-by-screen sweep of component files.
**Fix:** translate at the source (seed data) or add a centralized display-layer i18n map (e.g. in `lib/display.ts`) so cuisine values are translated once, not re-decided per screen.
**Command:** `/impeccable clarify` scoped to `packages/db/src/seed*.ts` + restaurant cuisine copy.

### [P1] Occasion-tag vocabulary is inconsistent between the rank flow and the restaurant profile
`RANK_TAGS` (Spanish, `RankAPlace.tsx:53`) and the seed's `TAGS` const (English by explicit design comment, `seed-extra.ts:489-497`) are the same taxonomy in two languages. A user tags "Cena romántica" while ranking, then sees "Date Night" on the same restaurant's profile.
**Fix:** reconcile to one vocabulary — map seed values through the same i18n table proposed above, or replace the seed's English constants with `RANK_TAGS`' Spanish set directly.
**Command:** `/impeccable clarify`

### [P2] No path from a ranked place back to its own profile
`RankingRow` in `RankingsTab.tsx:230` is a plain `<div>` — only "editar nota"/"quitar" are actionable, no link to `/r/:id`. A user checking hours or wanting to reserve after ranking a place has to re-search from Feed/Explore.
**Fix:** wrap the row (outside the note-edit/remove controls) in `<Link to="/r/$id">`, matching feed-card behavior.
**Command:** `/impeccable polish`

### [P2] "nuevo en tu lista" shows on re-ranks of an already-ranked place
Confirmed live by A: re-ranking Ajuala (already at 7.9 with an existing note) still showed the compare-card subline "nuevo en tu lista" throughout. This is factually incorrect information shown during a documented, common flow (re-ranking a place you've been to again), not a copy nit.
**Fix:** add an `isRerank` branch in `PlaceStep`/`CompareCard` that swaps the subline when the place already has a ranking.
**Command:** `/impeccable audit` scoped to `RankAPlace.tsx` (`PlaceStep`, `CompareCard` usage)

### [P2] Pairwise comparison progress counter doesn't hold its promise
A watched "2 de 4" get followed by two more "4 de 4" screens in a single flow. Undercuts trust exactly at the highest-friction step of the core loop.
**Fix:** recompute the total from the live remaining-comparisons count rather than a fixed initial estimate, or switch to an indeterminate indicator if the binary-insertion algorithm can't guarantee a stable total upfront.
**Command:** `/impeccable audit` scoped to the pairwise-compare state machine + `PlaceStep`

### [P2] CheersButton's accessible name is English inside an otherwise Spanish accessibility tree
`aria-label="Cheers"` / `"Quitar cheers"` (`CheersButton.tsx:48`) — a screen-reader user hears one English word with no visible English text to explain it. Found independently by both assessments (A via persona testing, B via source read), which is a good sign it's a real, not speculative, issue.
**Fix:** localize to `"Brindar"` / `"Quitar brindis"` (or whatever term matches the button's visible icon/label elsewhere in the app).
**Command:** `/impeccable clarify`

### [P2] The exported share-card tagline is English
`lib/shareCard.ts:76` bakes "where your friends actually eat" into the canvas-rendered PNG that gets shared outside the app — this is the one language miss that a non-user (the share recipient) will actually see.
**Fix:** localize the baked tagline to match the app's Spanish voice.
**Command:** `/impeccable clarify`

### [P3] Streak abbreviation is ambiguous
`RankingsTab.tsx:99` shows `"5s 🔥"` while `ProfileTab.tsx:138-139` spells out the same value as `"5 semanas"`. "s" isn't a standard Spanish abbreviation for "semana" and could read as seconds.
**Fix:** spell out consistently, or drop the letter and rely on the flame glyph alone.

### [P3] Scattered small English strings
`DiscoverTab.tsx:274` raw `dishGrain` ("film · daylight"); `DishCompose.tsx:15-16` grain-picker chips ("Candlelit"/"Daylight" next to Spanish "Ninguno"); `lib/time.ts:6` returns bare `"now"` for very recent timestamps.
**Fix:** batch these into the same pass that handles the P1/P2 data-layer items above — same root cause (sweep stopped at component-owned copy).

## Persona Red Flags

**Alex (Power User):** The Find-step front-loads a search box plus 7 filter chips (Cerca, Abierto ahora, Reservar, 4× price tier) at the very first decision point of the core loop — more upfront surface than a power user wants for a "find it, rank it fast" action. The unreliable pairwise counter (P2) reads as the system not knowing its own state, which erodes trust for an efficiency-minded user specifically.

**Jordan (First-Timer):** The core loop's copy is genuinely first-timer-friendly. But nothing explains *why* the pairwise "¿Cuál estuvo mejor?" comparisons determine the score — a first-timer has to infer the mechanic from the reassurance microcopy alone. English cuisine labels ("Basque," "Contemporary") will read as broken/untranslated to a Spanish-first newcomer, undermining trust in what otherwise looks like a polished product.

**Sam (Accessibility-sensitive):** `--text-muted` is deliberately tuned for contrast, `:focus-visible` rings are implemented globally, most interactive elements carry proper `aria-label`s. The CheersButton's English `aria-label` (P2 above) is the one confirmed gap — a screen-reader user hears an English word mid-flow with nothing visible to explain it.

**Riley (Stress Tester):** The headline fix (commit-at-reveal surviving an interrupted flow) held up under testing. Found two real cracks: the pairwise counter (P2) and the "nuevo en tu lista" mislabel on re-ranks (P2) — both are the UI actively showing something untrue about state, which is exactly the class of bug a stress-tester is meant to surface.

**Casey (Distracted Mobile User):** Primary actions sit correctly in the thumb zone throughout. The architecture is now interruption-safe by design — the ranking commits at reveal, so getting pulled away mid-note-step only costs the optional note/tags/dish, never the ranking itself. This is the single strongest improvement for this persona specifically.

## Minor Observations

- `/map` is a stylized dot-cluster illustration rather than a literal MapBox layer; tapping a dot routes to a generic `/explore` list rather than filtering to that spot/neighborhood — more decorative than functional as navigation right now (unchanged from baseline, not a regression).
- A brief photo-swap glitch was observed once during a `CompareCard` transition (previous opponent's image lingering with the new opponent's name) — `CompareCard.tsx` has no explicit loading/placeholder state on its `background-image` div; possibly just network latency in the test session rather than a reproducible bug, worth a second look under throttled network.
- "Reservar"/"Pedir"/"Cerca" quick-action pills appear present but their live-integration status wasn't reverified this pass (matches prior project note that reservations are inert-by-design for this phase).
- Settings' "Eliminar cuenta" flow is present with appropriately serious copy; the confirmation step wasn't clicked through to avoid affecting the shared demo account mid-review.

## Questions to Consider

- Is restaurant `cuisine` meant to become a controlled, translatable enum, or is it expected to eventually come from a real external data source (Google Places, etc.) that would need its own translation layer rather than a one-time fix?
- `RANK_TAGS` and the seed's occasion tags look like two independently-authored taxonomies that happen to overlap — worth unifying into one canonical list so what a user tags while ranking actually matches what a spot is "known for" on its profile?
- Now that the core loop's social payoff is solid, is there appetite for a lightweight first-run explainer for the pairwise comparison mechanic specifically, since it's the one step in an otherwise self-evident flow that isn't self-evident?
